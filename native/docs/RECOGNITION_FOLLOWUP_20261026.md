## Reproduced failure and smallest root repair

At source `76df4ed6886d8fe0e5bcc43852ce1ebbf9ca45b1`, `PhoneRecognitionProbeTest.stagedInputHandoffIsReadable` reproduced the earlier recorded-video failure with a 310-byte synthetic manifest and no model/video. The actual app process and application both had UID 10416; its own external directory was readable, but `Os.stat` on the staged manifest returned errno 13 (`EACCES`), the Java open failed and `isFile/length` appeared false/zero. Parsing and inference were never reached. Earlier non-isolated-storage invocation had failed too. This is proven cross-identity input access failure, not evidence of malformed JSON or a broken model. The device's precise FUSE/SELinux policy rule was not extracted.

The QA package intentionally rejects debugging; `run-as` confirmed that boundary. Changing its permissions, debuggability or file-size guard would hide the handoff defect. The repair streams fixed approved names from `/data/local/tmp/sign-recognition-<32-hex-token>` through instrumentation's shell pipe into a fresh app-private cache stage. Raw SHA256 and actual byte limits are checked before publishing each input. Only the bounded manifest's reviewed model/tracker/label pins and approved clip aliases are accepted. Results use an app-created `recognition-results` directory. Ordinary success/failure closes streams and removes the known private stage. An explicit same-token instrumentation cleanup handles interrupted runs; process death does not magically execute `finally`.

The new operator verifies the installed app/test hashes and exact source receipt, gates on Home/no active instrumentation, stages only validated files in a fresh token directory and selects one test method. It checks JUnit output as well as ADB's exit status: the reproduced failure had ADB exit 0. Cleanup failures or foreground takeover leave the overall run failed/pending. It never returns another agent's foreground app to Home. No recursive deletion of unknown directories is used.

The cascade found and repaired operator regressions before device use: current receipt fields differed from a historical receipt; Windows-only fixtures could not run in Linux CI; successful test output concealed failed cleanup; and a foreground check before a cleanup operation did not protect a later Home action. Tests demonstrated the last two failures before repair. Thirteen operator tests and independently executed actual Java staging tests pass locally. Initial helper/runner RED records were missing-implementation failures; the physical `EACCES` run is the meaningful reproduction of the original defect.

## Continuous translation: useful lead, missing proven input contract

The pinned [YT-ASL T5 checkpoint](https://huggingface.co/FatimahEmadEldin/ytasl-t5-v1_1-base/tree/cc6330e8a992975b80bf95b098cdf27f8379febe) declares CC BY 4.0 and contains a 990,988,976-byte F32 weight file, tokenizer and custom Python wrapper. Only its small source/configuration files were downloaded. The wrapper applies a learned 208-to-768 projection and T5 encoder-decoder generation. It requests the base configuration by model name and creates its own generation configuration; a fully local conversion must freeze those dependencies and prove generation parity rather than assume every JSON setting is honored. No Android export or useful benchmark is supplied by that card. The card's random-input example establishes neither signing input nor translation quality.

A related [training repository](https://github.com/signforall/t5-training-scripts) points to [JSALT PoseEstimation](https://github.com/JSALT2024/PoseEstimation). That pipeline's 208 values are 25 pose, 21 right-hand, 21 left-hand and 37 selected face points, each with x/y, plus specific crop, shoulder/group normalization and padding behavior. This contradicts reading 208 as only hands/body. It is a candidate contract: the inspected checkpoint does not prove that these exact options produced its training features. Never flatten the app's 543/553-point xyz array into 208 or guess missing coordinates. Neither related code tree showed a license file in the bounded review; no code was copied.

The next defensible experiment needs the checkpoint-specific extraction/normalization configuration and at least one reference clip with its 208-feature tensor and expected tokens. Then run an offline reference, export/quantize encoder and decoder with the tokenizer/cache behavior, and measure phone resources and sentence errors. A related architecture is not a ready mobile translator. Google's [official Gemma release log](https://ai.google.dev/gemma/docs/releases) supplies no downloadable SignGemma release in the inspected scope; it cannot presently be selected as an evidenced dependency. Other investigated large adapters do not remove these contract, rights, mobile and quality requirements.

The privacy guide also still marked real TTS capture testing inapplicable because no engine existed. That historical statement contradicted the implemented Pocket path. The current scope and matrix now require app-UID Pocket capture testing; muted AudioTrack progress is explicitly insufficient. Historical artifact results remain named and unchanged.
